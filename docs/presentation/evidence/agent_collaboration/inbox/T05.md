# T05 — append Traps 25-30 to `docs/LESSONS_LEARNED.md`
Docs only. Do not touch any other file. Match the format of `### Trap 24` at the bottom of the file
(heading `### Trap N: <title> (BL-069, 2026-09-25)`, then bullets: **Symptom/Observation**, **Cause**, **Resolution / How to avoid**).
Use ONLY the facts below; add no numbers, paths or claims that are not listed. Keep each trap to 5-9 lines.

Trap 25 — Signed images are always a multiple of 4096 bytes. FACT: espsecure pads the data to a 4096 multiple and
appends a whole 4096-byte signature sector, so a signed IDF app image is always sector aligned (v1 = 1,249,280 B = 305
sectors). The bootloader reads only up to ALIGN_UP(end,4096) plus the signature block. Consequence: BLE OTA refuses
non-aligned images host-side (`host/labflash/update.py`), and "non-aligned" test images cannot come from a normal build.

Trap 26 — A post-signature trailer is invisible to the bootloader but espsecure refuses it. FACT: bytes appended after
the signature sector are never read by the bootloader, so a trailer makes a valid image whose file size is not a 4096
multiple; `espsecure verify-signature` refuses such a file, so `labflash.imagefmt.verify_device_signature` strips the
trailer before verifying. STATUS: NOT YET CONFIRMED ON HARDWARE. Gate R1 (append 4096 B to v1, install over WiFi, expect
boot + confirmed=1) is still pending; say so plainly in the trap.

Trap 27 — An over-limit image fails in three places and the BLE symptom is silent. FACT: rejected by BLE `ota_begin`
(fw_len > partition size), by WiFi `esp_ota_begin`, and by the bootloader (FAIL_LOAD). Over BLE the transport still
ACKs sectors, so the symptom is no reboot and a host timeout, not an error message. Use a short timeout for images
expected to be rejected.

Trap 28 — IDF's own size check refuses an over-partition build, and its error is on stdout. FACT: `check_sizes.py`
fails the build when the signed image exceeds the 4 MB app partition; the message ("All app partitions are too small
for binary ... size 0x...") is written to the build's STDOUT log while stderr only holds Kconfig notes, so an error
message built from stderr alone hides it. The too_big pool image is therefore built against a temporary 5 MB
partition table (`genvariants.BIG_PARTITIONS`); `build_idf_image` now includes the last 40 stdout lines in BuildError.

Trap 29 — Image size grows in 64 KiB steps, so an exact byte target is not reachable. FACT: flash-mapped segments are
64 KiB aligned; a 4096-byte pad increase produced the same signed size (observed: pad 2,879,488 and 2,883,584 both gave
4,132,864 B). The near_limit image therefore targets a window just under 4 MiB (built: 4,132,864 B) and too_big a window just
over (built: 4,263,936 B), via `genvariants.solve_pad` with `SIZE_WINDOW` = 64 KiB.

Trap 30 — Same seed, same image: compare content_sha256, not sha256. FACT: RSA-PSS signatures are salted, so two builds of
the same seed differ in the signature sector only. Observed: rebuilding pool image g00 into a different output directory gave
byte-identical content for the first 2,031,616 bytes and 388 differing bytes inside the signature sector. The manifest
therefore carries `sha256` (whole file) and `content_sha256` (everything before the signature sector); reproducibility
is judged on content_sha256. Also: `idf.py` runs from `esp_idf/`, so a relative `--out` path resolved against the wrong
directory until `genvariants.run` made it absolute.
