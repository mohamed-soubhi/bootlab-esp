## Design notes
- `validate_manifest` check order (chosen so each parametrized case's expected message is the one raised):
  schema → images list → duplicate `version` → duplicate `file` → per-entry `sha256` → per-entry `size` type →
  `index` sequence → per-entry `expected` rules (`too_big` claims → `unaligned_trailer` ble claim → `aligned` →
  `slot`) → count `< min_valid` (`"12"`) → distinct sizes (`"spread"`).
- Alignment check applies only to roles `valid`/`near_limit`, so an `unaligned_trailer` entry (whose whole point
  is a non-4096 size) is not flagged, per spec.
- The `slot` bound comes from `m["slot_size"]`, defaulting to `SLOT_SIZE` when the key is absent.
- `write_manifest` validates before `write_text`, so a rejected manifest never creates the file.
- JSON is `indent=2, sort_keys=True` plus a trailing newline; no timestamps or date keys are written.

## Doubt (not a deviation, flagged for the lead)
- `_check_size` also rejects `bool` for `"size"` (a `bool` is an `int` in Python). The spec only says "not an int";
  no test exercises `size=True`, so this is strictly tighter, not looser.
- `expected_outcomes` uses `trailer_len` only in the `unaligned_trailer` reason text; for the other roles the
  reason is geometric, which matches the test's "non-empty string" requirement.
